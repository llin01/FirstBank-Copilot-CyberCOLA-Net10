# HSM、NCCC 與 FISC 規格待確認事項

第一銀行信用卡自建案 · CyberCOLA 測試環境 · 2026-11-05

授權系統在測試環境驗證時，發現三處實際行為和規格書對不起來（第三項 FISC 0120 於 2026-11-18 新增）。請各負責單位確認以哪一方為準，我們再依結果調整模擬器與測試工具。本文件不含卡號、帳號或連線資訊。

---

## 一、SocketClient.dll 與《HSM 介面建議書 V2.5》不一致

**致：HSM 廠商（Provision）**

Auth 使用的 HSM 用戶端原為 `SocketClient.dll` 1.0.0.3，2026-11-06 起改為 1.0.0.6（設定讀取 `D:\NCARD_EXE\ProHSM\config.ini`）。我們以測試用連線埠回傳特定內容，觀察這支 DLL 實際如何解析回應，結果與 V2.5（2023/6/28）有以下差異：

| 項目 | V2.5 規格書 | SocketClient.dll 實際行為 |
|---|---|---|
| 請求開頭 | 未說明傳輸格式 | 第 1 個 byte 為功能編號（binary，例如 0x01），之後才是欄位 |
| rtnCode | char 2，`00` 表示成功 | 回應第 1 個 byte 為 binary 回傳碼，DLL 再轉成 2 字元；以 ASCII 傳 `"00"` 會被讀成 30 |
| rsnCode | char 8 | 一致（8 字元） |
| **Func 01 GenerateCVV · cvv** | char **5** | 讀 **3** 字元 |
| **Func 03 EncryptBankPin · Pin_offset** | char **4** | 讀 **6** 字元 |
| Func 05 GeneratePVV | 4 / 4 / 4 | 一致 |
| Func 08 GenerateARPC · arpcData | 16 | 一致 |
| Func 09 GenerateCAVV · cavv | 3 | 一致 |
| 設定檔位置 | 未說明 | 寫死為 Windows 絕對路徑 `D:\NCARD_EXE\ProHSM\config.ini` 與 `suipenv.ini`，無法另行指定 |
| Func 07 VerifyARQC | cdolDataLength 2、cdolData n、arqcData 16、panData 18、CVN 2 | 1.0.0.3 固定複製 96 字元的 cdolData，其他長度都在 DLL 端被擋下（rtnCode `01`、rsnCode `01009999`）。**1.0.0.6 已改為依 cdolDataLength 變動**（十進位字元數，最多 99），與規格一致 |

> **2026-11-06 更新**：專案已換成 `SocketClient.dll` **1.0.0.6**，並移除 `SocketClient_update.dll`。比對 1.0.0.3 與 1.0.0.6 後，請求開頭、回傳碼的格式，以及 Func 01、Func 03 都沒有變；Func 07 已修正（見上表）。因此第 3、4 題已經解決，第 1、2 題仍待確認，另新增第 5 題（設定檔路徑）。

### 請確認

1. Func 01 的 CVV 與 Func 03 的 Pin_offset，正式 HSM 回傳的長度以哪一方為準？1.0.0.6 仍分別讀 3、6 字元。若以規格書為準，請提供對應的新版 `SocketClient.dll`。
2. 請求的功能編號 byte 與回應的 binary 回傳碼，是否為正式 HSM 的傳輸格式？若是，請補進規格書。
3. ~~Func 07 VerifyARQC 的輸入格式，能否提供一組可通過 DLL 檢核的範例？~~ 已由 1.0.0.6 解決：`cdolDataLength` 為字元數，`cdolData` 依此長度傳送。
4. ~~專案內另有 `SocketClient_update.dll`，是否還需要保留？~~ 已移除。
5. 設定檔路徑能否改為可設定（例如相對於程式所在目錄，或由環境變數指定）？目前寫死的 Windows 路徑使 Auth 無法在 Linux 上使用 HSM，也無法讓不同環境（測試、正式）在同一台主機上各自指向不同的 HSM。

## 二、0220 被拒時，0230 應回什麼回應碼

**致：NCCC 規格負責單位**

NCCC 壓力測試每輪約有 24 筆 0220（處理碼 000030、輸入方式 01）在授權端被拒，但 GW 送回給 NCCC 的 0230 回應碼都是 `00`：

| 來源 | 記錄內容 |
|---|---|
| 授權記錄（`COLA_TX_AUTH_TODAY`） | RESP = D、RESP_CODE `87`（部分為 `N0`）、CHECK_CODE `012`（資料驗證）、原因碼 `75` |
| 送回 NCCC 的 0230 | ResponseCode `00` |

同一輪其他 0220（處理碼 220030、020030、200030）皆為核准，0230 回 00，兩邊一致。

### 請確認

1. 依 NCCC 規格，0220（advice）被發卡行拒絕時，0230 應回 `00`（僅表示已收到）還是實際的拒絕碼（如 87）？
2. 若應回 `00`：拒絕結果只保留在授權記錄、不回給 NCCC，是否符合規格要求？
3. 原因碼 75 對應的資料驗證項目為何？是範本資料的問題，還是 0220 本來就不應做這項檢核？

## 三、FISC 0120 帶拒絕碼進來，授權端記為拒絕、0130 回 00

**致：FISC（財金）規格負責單位**（2026-11-18 新增）

FISC 壓力測試每輪有 4 筆 0120（處理碼 000000、輸入方式 07），送進授權端時 F39 已是 `54`（卡片過期）。授權端把它記為拒絕，但回給 FISC 的 0130 回應碼是 `00`：

| 來源 | 記錄內容 |
|---|---|
| FISC 送來的 0120 | F39 = `54` |
| 授權記錄（`COLA_TX_AUTH_TODAY`） | RESP = D、RESP_CODE `54`、CHECK_CODE `012`（資料驗證）、原因碼 `75` |
| 授權端回給 GW、再送回 FISC 的 0130 | ResponseCode `00` |

這個結果每一輪都相同：自 2026-10-28 起，測試庫裡所有 0120 都是這組記錄（D／54／012／75），沒有例外。和第二項不同，這裡的 `00` 是授權端（CyberAuthFISC）產生的，GW 只是轉送。另外，授權記錄的 RESP_CODE `54` 和 0120 帶進來的 F39 相同，看起來是照記 advice 原本的值，不是授權端自己判斷出的拒絕碼（尚未從程式確認）。

### 請確認

1. 依 FISC 規格，0120（advice）的 0130 是否一律回 `00`，只表示已收到？
2. 0120 的 F39 已經是拒絕碼（代行授權已拒絕）時，發卡行是否還應該再做授權檢核？授權記錄應記為拒絕，還是只記下這筆通知？
3. 原因碼 75 的資料驗證，是否本來就不應套用在 0120？這和第二項 NCCC 0220 的原因碼 75 是否為同一個檢核？

---

確認結果請回覆給系統負責人。HSM 部分若以規格書為準，需同步更新模擬器（WpfHSMSimulator）；NCCC 與 FISC 部分會影響測試工具對 0230、0130 的成功率統計。
